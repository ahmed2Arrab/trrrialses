# بنية التطبيق

## نظرة عامة

يتكون المشروع من تطبيقين يعملان معًا:

1. **خادم Node.js/Express** في `index.js`: مصادقة أولية، API، حفظ البيانات والملفات على القرص، والنسخ الاحتياطي.
2. **واجهة React وTypeScript** في `frontend/`: واجهة RTL تعرض لوحة العملاء والتفاصيل، وتتصل بالخادم باستخدام Axios.

يحتوي `client/` على واجهة HTML/CSS/JavaScript أقدم. يخدمها Express كبديل إذا لم يكن `frontend/dist` موجودًا. لا تُبنى هذه الواجهة بواسطة Vite.

## تدفق التشغيل

1. يقرأ الخادم `PORT` (أو يستخدم 3000)، وينشئ مجلدات البيانات والملفات إن لم تكن موجودة.
2. يحاول إنشاء حساب المدير الأول إذا لم يوجد ملف المستخدمين. يتطلب ذلك `INITIAL_ADMIN_USERNAME` و`INITIAL_ADMIN_PASSWORD`.
3. عند وجود `frontend/dist`، يقدّم Express ملفات البناء، ثم يعيد `index.html` لمسارات SPA. خلاف ذلك يقدّم `client/`.
4. ترسل واجهة React طلباتها إلى عنوان نسبي من نفس الأصل، ما لم يُضبط `VITE_API_URL`.
5. بعد تسجيل الدخول، تُحفظ بيانات المستخدم في `localStorage` عبر Zustand persist. عند تحميل التطبيق، يتحقق العميل من اسم المستخدم عبر `/api/me` ثم يحمل بيانات العملاء.
6. تعديلات بيانات العميل تُحدّث حالة Zustand أولًا، ثم يرسل المتجر كامل قائمتي العملاء والمهملات إلى `/api/data`.

## التخزين المحلي

ينشئ الخادم البيانات تحت `data/` في جذر المشروع:

```text
data/
  db/
    delta_db.json       العملاء النشطون
    delta_trash.json    العملاء المنقولون إلى المهملات
    delta_users.json    المستخدمون وكلمات المرور المجزأة
  files/                المرفقات المرفوعة
```

`data/` متجاهل في Git. ملفات العملاء والمستخدمين والمرفقات تبقى على الجهاز الذي يشغّل الخادم، ولا تنتقل إلى المتصفحات أو GitHub إلا عبر النسخة الاحتياطية أو عمليات API. لا يناسب تخزين JSON عمليات الكتابة المتزامنة الكثيفة أو عدة خوادم تشترك في البيانات.

## نموذج البيانات

### المستخدم

```ts
type UserRole = "admin" | "accountant" | "admin_readonly" | "staff";

interface User {
  id: string;
  username: string;
  name: string;
  role: UserRole;
}
```

ملف الخادم يضيف `password` (bcrypt hash) و`createdAt`. لا تعيد API كلمة المرور للواجهة. يدعم الإعداد الحالي إنشاء مدير أول واحد فقط؛ لا توجد شاشة أو endpoint لإنشاء المستخدمين أو تغيير كلمات المرور.

### العميل

```ts
interface Client {
  id: string;
  name: string;
  plot: string;
  totalContract: number;
  paid: number;
  phone: string;
  expenses: Expense[];
  tips: Tip[];
  payments: Payment[];
  docs: Document[];
  pdfs: FileRecord[];
  receipts: FileRecord[];
}
```

- `Expense`: `reason`, `amount`, `date`.
- `Tip`: `reason`, `payer`, `amount`, `date`.
- `Payment`: `id`, `receiver`, `amount`, `date`.
- `Document`: `person`, `name`, `purpose`, `place`, `date`.
- `FileRecord`: `filename`, `originalName`, `date`, `path`.

تملأ `normalizeClient` الحقول الغائبة بقيم افتراضية، وتحول الأرقام إلى `number` والنصوص إلى `string`. يفيد ذلك في قراءة سجلات قديمة أو ناقصة.

## منطق الأرقام المالية

الدوال المرجعية موجودة في `frontend/src/utils/clientModel.ts`:

- إجمالي المصروفات = مجموع `expenses[].amount`.
- إجمالي الإكراميات = مجموع `tips[].amount`.
- المبلغ المعروض كمدفوع في تفاصيل العميل:
  - إذا وُجد سجل دفع واحد أو أكثر: مجموع الدفعات + `client.paid` − المصروفات.
  - وإلا: `client.paid` − المصروفات.
- عمود «المتبقي» في لوحة العملاء = `client.paid` − المصروفات.

هذه الأرقام هي قواعد العرض الحالية في الواجهة. ينبغي مراجعة معنى الحقول المحاسبي قبل تغيير المعادلات أو استيراد بيانات جديدة؛ أسماء `paid` و`totalContract` لا تفسر وحدها جميع الاستخدامات المالية.

## التوجيه والصفحات

- `/login`: تسجيل الدخول.
- `/dashboard`: قائمة العملاء والبحث والمهملات.
- `/client/:clientId`: تفاصيل العميل.
- `/`: يحوّل إلى لوحة التحكم عند وجود مستخدم محفوظ أو إلى صفحة الدخول.

`ProtectedRoute` يمنع التنقل إلى صفحات معينة من الواجهة عند عدم وجود مستخدم محلي محفوظ. هذا ليس بديلًا عن التحقق على الخادم؛ راجع [ملاحظات الأمان](SECURITY.md).

### مسؤوليات الصفحات

- **لوحة التحكم:** بحث مؤجل زمنيًا بالاسم أو رقم القطعة أو الهاتف، عرض 20 عميلًا في الصفحة، وضع داكن، إضافة عميل، نقل العميل إلى المهملات، عرض المهملات واستعادة/حذف عميل نهائيًا. تعرض أيضًا عناصر النسخ الاحتياطي والاستعادة بحسب دوال صلاحيات الواجهة.
- **تفاصيل العميل:** تعديل الهاتف والعقد والمدفوع، تسجيل المصروفات والإكراميات والمدفوعات، تحرير المستندات، إدارة ملفات PDF والإيصالات، معاينة الملفات، تنزيلها وتوليد كشف حساب PDF.
- **تسجيل الدخول:** إرسال اسم المستخدم وكلمة المرور إلى الخادم، ثم تخزين بيانات المستخدم العامة في Zustand persist عند النجاح.

تُخزن الإكراميات في `tips` ويعرضها الكود في بطاقة بعنوان «المتبقي على العميل (دين)»؛ راجع تعريف الحقول ومعادلات الأرقام أعلاه قبل تفسير هذه البطاقة كمعلومة محاسبية.

## الأدوار في الواجهة

| الدور | ما تعرضه قواعد الواجهة |
|---|---|
| `admin` | عرض الماليّات والتعديل والحذف والنسخ الاحتياطي والوصول إلى المهملات. |
| `accountant` | مثل المدير في دوال الصلاحيات. |
| `admin_readonly` | عرض الماليّات والمهملات، دون تعديل أو حذف أو نسخ احتياطي. |
| `staff` | معلومات غير مالية حسب عناصر الصفحة؛ لا تسمح دوال الصلاحيات بالتعديل. |

هذه قواعد إظهار/إخفاء UI فقط؛ خادم Express الحالي لا يفرضها على مسارات API.

## الواجهة القديمة

إذا لم يوجد `frontend/dist`، يقدّم الخادم `client/index.html` وموارده. قد يختلف سلوك الواجهة القديمة عن React؛ توثيق المسارات والواجهات في [API.md](API.md) يصف خادم Express المشترك.
