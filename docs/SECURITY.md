# الأمان والقيود التشغيلية

هذه الصفحة توثق السلوك الموجود لمساعدة المشغلين والمطورين على تقييمه. ليست شهادة أمان، ولا تجعل التطبيق مناسبًا تلقائيًا للاستضافة العامة أو لبيانات حساسة.

## تنبيهات مهمة قبل الاستخدام

### 1. لا توجد حماية API فعلية بحسب الدور

تُخفي `frontend/src/utils/permissions.ts` بعض الأزرار أو المحتوى، وتمنع `ProtectedRoute` فتح صفحات React دون مستخدم محفوظ في المتصفح. لكن هذه إجراءات واجهة فقط. مسارات مثل `/api/data`, `/api/upload`, `/api/backup`, `/api/restore`, `/api/delete-pdf` و`/api/permanent-delete-client` لا تتحقق من الجلسة أو دور المستخدم في Express.

`/api/me` لا يتحقق إلا من اسم مستخدم مرسل في `x-username`; لا يصدر الخادم رمز جلسة أو token. لا تعتبر تسجيل الدخول الحالي حدًا أمنيًا لحماية البيانات من عميل HTTP مباشر.

**النتيجة:** لا تعرض هذا الخادم على الإنترنت أو شبكة غير موثوقة ببيانات حقيقية قبل تنفيذ مصادقة خادمية، جلسات آمنة، وتفويض لكل endpoint.

### 2. فحص ترخيص خارجي قد يحذف البيانات

عند بدء الخادم، ثم كل ساعة، يطلب `index.js` ملف حالة ترخيص من عنوان GitHub ثابت. إذا كان الرد يحمل `status: "locked"`, ينفذ الخادم حذفًا تكراريًا لمجلد `data/` ثم ينهي العملية. عند فشل الاتصال يسجل تحذيرًا ويواصل العمل.

هذا السلوك قد يحذف العملاء والمرفقات والمستخدمين محليًا، ولا يقتصر على إيقاف الخدمة. احتفظ بنسخ احتياطية خارج مجلد المشروع، وراجع مصدر/سلوك الخدمة الخارجية قبل الاستخدام. لا تغيّر عنوان الخدمة أو السلوك دون فهم أثر ذلك على الترخيص والتشغيل.

### 3. كلمات المرور وحسابات المستخدمين

- يُنشأ المدير الأول من `INITIAL_ADMIN_USERNAME` و`INITIAL_ADMIN_PASSWORD` عند غياب ملف المستخدمين.
- يتحقق الخادم من حد أدنى 12 حرفًا، ثم يخزن bcrypt hash.
- بعد إنشاء قاعدة المستخدمين، لا تنفذ متغيرات البيئة إعادة تعيين كلمة المرور.
- بيانات المستخدمين محفوظة في `data/db/delta_users.json`; احمِ هذا الملف ونسخه الاحتياطية.
- إعداد إنشاء المستخدمين الحالي لا يوفر شاشة لإدارة الحسابات أو استعادة كلمة المرور.
- لا تستخدم كلمة مرور حقيقية سابقة أو معاد استخدامها، ولا تحفظ الأسرار في GitHub أو ملفات `VITE_*`.

## حدود تنفيذ يجب تقييمها قبل النشر

الملاحظات التالية مستخلصة من مسارات الخادم الحالية، وتحتاج معالجة هندسية قبل اعتبار الخدمة آمنة:

- `cors()` مفعّل دون تقييد أصول محددة.
- `/api/data` يعيد جميع بيانات العملاء، و`POST /api/data` يستبدل القائمتين كاملتين دون تحقق صلاحيات أو تحقق بنية/ملكية.
- `/api/backup` و`/api/restore` غير محميين خادميًا؛ الاستعادة تستخرج ZIP إلى مجلد البيانات.
- رفع الملفات يسمح بمجموعة امتدادات، لكنه لا يحدد حدًا واضحًا لحجم الملف أو يتحقق من محتوى الملف الفعلي.
- `/api/pdf-data` يستخدم اسم ملف من الطلب لبناء مسار التخزين؛ ينبغي حصر الاسم على ملفات مملوكة ومعروفة ومنع أي تجاوز للمسار.
- عمليات JSON المتزامنة قد تتسابق أو تفقد تحديثات؛ التخزين ليس قاعدة بيانات معاملات.
- حجم JSON وURL-encoded مضبوط على 50 MB؛ راجع هذا الحد مع أحجام البيانات والملفات الفعلية.
- الأخطاء في بعض endpoints تعيد رسالة عامة ولا تسجل التفاصيل، ما يجعل التشخيص التشغيلي محدودًا.

لا يُقصد من هذه القائمة أنها استعراض أمني كامل أو ترتيب للأولويات. نفّذ مراجعة أمنية واختبارات قبل نشر الخدمة.

## ممارسات تشغيل مقترحة

1. اربط الخادم بواجهة محلية/شبكة خاصة حتى إتمام الحماية الخادمية.
2. استخدم HTTPS عند الاتصال عبر شبكة، واحمِ الوصول إلى النظام والنسخ الاحتياطية.
3. أنشئ نسخًا دورية خارج مجلد التطبيق، واحتفظ بنسخ تاريخية غير قابلة للتعديل.
4. لا ترفع `data/`, `.env`, السجلات أو النسخ الاحتياطية إلى مستودع عام.
5. راجع تاريخ Git لأي أسرار سابقة؛ حذف الملف من آخر commit لا يمسحه من commits الأقدم. دوّر أي بيانات اعتماد ظهرت علنًا.
6. اجعل مدير النظام يراجع خدمة الترخيص ومصدرها وسلوك حذف البيانات قبل التشغيل.
